# LocalPolish 1.0.0 audit

Audit date: 18 October 2026, Africa/Cairo.
Release: `v1.0.0`, commit `71d5cbf4fca3ff05dfc81c36b2f831b5a51ddef4`.
Status: audit complete. Fixes and features are proposals, not implemented changes.

The next release needs privacy and draft-safety fixes before more features. The existing checks all pass, but extra checks found gaps in iframe blocking, settings saves, text replacement, and bridge cleanup.

This report lists 22 findings. Three are P1, fifteen are P2, and four are P3. Each has a task in the [next-release plan](../plans/next-release.md). Feature ideas and optimizations are separate from defects.

## Scope and evidence

I inspected the extension entrypoints, content scripts, settings, prompts, output cleanup, provider adapters, native bridge, installers, tests, CI, release files, and privacy claims. I also checked the published release and the repository's current GitHub settings.

The release zip was downloaded from [LocalPolish 1.0.0](https://github.com/ashahinL/localpolish/releases/tag/v1.0.0). Its SHA-256 is:

```text
c097e5bb315feb06ce97d92d6b11054b89471a3b805fec47b7cc4a40cd7326d7
```

All 15 files in the zip match a fresh local build byte for byte. The expanded extension is 147,897 bytes. The zip is 58,035 bytes. Browser privacy probes loaded the extracted release into a fresh Chromium profile.

The checks ran on macOS with Node `26.10.0` and npm `11.19.1`. The installed CLI versions were Claude Code `2.1.300`, Codex `0.162.1`, and Grok `1.0.62`. Version checks do not establish that rewriting works with those CLIs.

The skipped local unit test is in the Windows installer group. CI runs on Linux, where the macOS and Windows installer groups do not run.

A targeted scan of tracked files found no matches for the checked GitHub token, Anthropic key, or private-key patterns. The final document formatting and link checks also passed.

Additional probes used fake keys, a local HTTP server, browser DOM fixtures, and harmless fake CLI processes. No real drafts or paid provider calls were used. Outputs are saved in [the evidence snapshot](1.0.0-evidence.json).

A Claude review and a Codex challenge independently agreed on the iframe blocklist, inherited spellcheck, and process cleanup issues. The final debate dropped an editor race because its proof used mocks. A later browser DOM probe reproduced a write into another editor, so A04 keeps that finding with its timing condition stated explicitly. The raw review is saved in [the debate record](1.0.0-debate.json).

## Priorities

- P1: a privacy or security boundary fails. Fix before the next public release.
- P2: a reproducible correctness, reliability, or release-control problem. Include in the next release unless explicitly deferred.
- P3: a smaller compatibility, warning, or documentation problem. Each still has a planned fix.

These priorities describe this project's impact. They are not vulnerability scores.

## Findings

### A01. Hidden sites still send text from embedded editors

Priority: P1. Evidence: released extension and source. Task: T15a.

`src/entrypoints/content.ts:27-30` injects into all frames, including blank frames. Lines 67-70 check only the current frame's `location.hostname`.

Reproduction: block `localhost`, open a page there containing an editor iframe served from `127.0.0.1`, type at least four words inside the iframe, and pause. The released extension sent one automatic rewrite request. Blank and `srcdoc` frames also have an empty hostname, which cannot match the parent site's blocklist entry.

Fix: apply site policy to both the top-level tab and the editor frame. Derive the tab and frame identity from Chrome's sender metadata. Keep the documented shortcut exception. Do not fix this by rejecting every rewrite on blocked sites, since that would also break the shortcut.

Verification: no automatic requests from same-origin, cross-origin, blank, or `srcdoc` frames on a hidden tab. A manual shortcut still works.

### A02. Blocking a site leaves an active idle marker behind

Priority: P2. Evidence: released extension. Task: T15b.

`src/content/idle.ts:228-248` can start a request from a marker without checking `deps.isEnabled()`. `renderMarks()` does not hide marks when the setting changes. The content settings refresh does not cancel existing idle work.

Reproduction: get a fix marker, add the current site to the blocklist, change the text, and click the old marker. The marker remained visible and sent one new request after blocking. This probe involved an explicit click, not a new automatic request.

Fix: refresh existing UI when site or idle settings change. Hide idle markers and cancel their timers and requests when disabled. Recheck eligibility before marker activation. Preserve the separate manual shortcut path.

### A03. Inherited spellcheck settings do not stop automatic fixes

Priority: P1. Evidence: browser DOM and source. Task: T15c.

`src/content/editable.ts:53` checks only the field's own `spellcheck` attribute.

Reproduction: put a textarea inside `<div spellcheck="false">`. Chromium reports `textarea.spellcheck === false`, but `isIdleField(textarea)` returns `true`. A field the page excluded from spellchecking remains eligible to send text automatically. This contradicts `PRIVACY.md:48-50`.

Fix: check the effective `spellcheck` property. Cover inherited false, explicit false, and a child that explicitly turns spellcheck back on.

### A04. Accept can paste into another editor during its wait

Priority: P2. Evidence: controlled browser DOM reproduction. Task: T15d.

`src/content/editable.ts:216-226` checks the selection, waits 50 milliseconds on the Lexical and Draft.js path, and then calls `paste()`. Lines 247-258 use the live global selection without checking that it still belongs to the captured editor.

Reproduction: start Accept in editor A, move focus and the selection to editor B during that wait, and let B handle the paste event. B's `newer unsaved draft` became `Old draft text`, the rewrite intended for A. The function returned `rejected` after B had already changed.

This needs a selection or editor change during the wait. The browser fixture scheduled that change deliberately. It was not reproduced on a live Gmail, X, or LinkedIn composer.

Fix: check the editor, both selection endpoints, selected text, and relevant draft snapshot immediately before each write. Reject stale work before dispatching the paste. A post-write check cannot prevent this loss.

### A05. Changed line breaks pass the stale-text check

Priority: P2. Evidence: browser DOM reproduction. Task: T15e.

`src/content/editable.ts:216` compares rich text through `normalize()`. Lines 282-283 collapse all whitespace, including line breaks.

Reproduction: capture two paragraphs containing `hello world` and `line two`. Before Accept, change the paragraph split to `hello` and `world line two`. Accept reports success and restores the old split while applying the rewrite. The intervening layout edit is lost because both drafts normalize to the same words.

Fix: compare a consistent rich-text representation that preserves line breaks. Normalize only browser artifacts the application intentionally treats as equivalent. Keep the existing paragraph and blank-line regression tests.

### A06. A remote hostname can pass the loopback API-key check

Priority: P1. Evidence: provider function with a fake network boundary. Task: T15f.

`src/background/providers/openai.ts:11` treats every hostname beginning with `127.` as local.

Reproduction: set the base URL to `http://127.audit.invalid/v1` and use a fake key. The provider attempted a request with `Authorization: Bearer fake-audit-key`. The probe intercepted fetch, so no key left the machine. A domain starting with `127.` is not necessarily a loopback IP address.

Fix: distinguish parsed IPv4 addresses from domain names. Permit HTTP keys only for actual loopback addresses and the intended localhost names. Reject other protocols before fetch. Keep LAN servers without keys supported as documented.

### A07. A CLI descendant can survive cancellation

Priority: P2. Evidence: real bridge process and fake CLI. Task: T15g.

`bridge/host.mjs:173-174` schedules a process-group SIGKILL after SIGTERM. Lines 186 and 244 clear that timer when the direct child exits.

Reproduction on macOS: a fake CLI starts a child with independent standard streams that ignores SIGTERM. Disconnect the bridge input. The CLI and bridge exit, but the descendant is still alive after the two-second escalation deadline. The audit killed the test process afterward.

Fix: finish process-group cleanup before the bridge exits. The leader exiting does not prove that the whole group exited. Test a resistant descendant and the Windows process-tree path separately.

### A08. The macOS wrapper expands shell syntax in file paths

Priority: P2. Evidence: installer function and generated wrapper. Task: T15h.

`bridge/install.mjs:65` puts paths inside shell double quotes without escaping shell expansion characters.

Reproduction: install into a temporary repo directory named `repo-$(touch expanded)`, then run the generated wrapper. The shell created the harmless `expanded` marker and the wrapper failed. The directory name ran as shell syntax.

This requires an unusual installation path. It is not proof that a website can execute shell commands through the extension.

Fix: quote each generated shell argument as a literal, including PATH values. Cover spaces, quotes, dollar signs, backticks, and non-ASCII paths. Retain the Windows shim tests.

### A09. Settings from two windows can overwrite each other

Priority: P2. Evidence: settings function with a storage boundary. Task: T16a.

`src/core/settings.ts:108-126` reads the whole settings record, merges a patch, and writes the whole record. `src/options/useSettings.ts:34` queues saves only within one mounted page.

Reproduction: concurrently save `{ idleFix: false }` and `{ defaultMode: 'shorter' }`. The final state is `idleFix: true`, `defaultMode: 'shorter'`. One independent change disappeared. The popup and options page have separate queues.

Fix: give settings one writer across extension pages. Apply changes to individual model and effort entries as well as top-level fields. Keep base URL and key clearing in the same update, so an endpoint change cannot retain another endpoint's key.

### A10. A failed save still allows Test connection to proceed

Priority: P2. Evidence: released options page with a rejected storage boundary. Task: T16b.

`src/options/useSettings.ts:45-50` clears pending keys before the save and turns rejection into a resolved promise. Test controls await that promise and continue.

Reproduction: reject `chrome.storage.local.set`, select a different model, then click Test connection. The page shows the new model and a save error, but still sends a test request. The background reads saved settings, so this can test the old configuration. The failed patch is no longer pending for a retry.

Fix: retain failed changes until saved or discarded. Return a failure result from `flush()`. Do not run a connection test against settings that failed to save. Show pending, failed, and saved states accurately.

### A11. Malformed saved settings can break the extension

Priority: P2. Evidence: settings functions. Task: T16c.

`src/core/settings.ts:70-103` casts most saved fields rather than validating them. A models object can contain null values, provider names can be unknown, and blocklist entries can be non-strings.

Reproduction: load a settings record with `blocklist: [null]` and a null Codex model. The null model survives loading. `isBlocked()` then throws `Cannot read properties of null (reading 'trim')`.

Ordinary pages were not shown to have access to this storage. The failure matters for damaged state, migrations, and any future import feature.

Fix: validate saved values at the storage boundary. Restore safe defaults for invalid fields while preserving valid settings. Use one normalization contract for reads and future imports.

### A12. Filtered partial output can become an accepted rewrite

Priority: P2. Evidence: provider and rewrite functions with a fake SSE response. Task: T16d.

`src/background/providers/openai.ts:79` returns on `[DONE]`. Lines 91-94 reject `length`, but do not reject `content_filter`.

Reproduction: return a partial text chunk with `finish_reason: 'content_filter'`, followed by `[DONE]`. `runRewrite()` emits `done` with that partial text, enabling Accept. OpenAI documents `content_filter` as output omitted by filtering in the [Chat API reference](https://developers.openai.com/api/reference/resources/chat).

Fix: treat explicit non-success finish reasons as failures. Preserve compatibility with servers that send a valid `[DONE]` without a finish reason. Keep partial output from becoming an acceptable final draft after an explicit failure.

### A13. Cleanup removes literal text tags from the user's content

Priority: P2. Evidence: cleanup function. Task: T16e.

`src/core/cleanup.ts:23-27` strips a complete `<text>...</text>` wrapper without checking whether it was already in the input.

Reproduction: `cleanOutput('<text>hello</text>', '<text>hello</text>')` returns `hello`. The model returned the input unchanged, but cleanup deletes the tags. This can damage markup examples and quoted instructions.

Fix: distinguish model-added wrappers from content already present in the original. Apply the same preservation rule to nested wrappers and fenced code.

### A14. Emoji warnings miss flags and skin-tone changes

Priority: P3. Evidence: token functions. Task: T16f.

`src/core/tokens.ts:22-24` matches extended pictographs, but not complete emoji sequences.

Reproduction: `findMissingTokens('hi 👍🏽 🇪🇬', 'hi 👍')` returns an empty list. The flag disappeared and the thumb's skin tone changed without a warning.

Fix: compare complete emoji sequences. Cover flags, skin tones, joined families, and keycaps. Keep duplicate handling deliberate. Do not add a large dependency without first checking browser-supported Unicode tools.

### A15. Some accepted site entries never block the site

Priority: P2. Evidence: site and blocklist functions. Task: T16g.

`src/popup/sites.ts:53-59` accepts almost any non-empty text without whitespace. The options page uses a separate parser.

Reproduction: add `example.com:8080/path`. The popup stores `example.com:8080`, but `isBlocked('example.com', list)` is false. The UI reports a saved entry that does not block the hostname.

Fix: share hostname parsing and validation between both settings pages and storage normalization. Handle schemes, ports, paths, IPv6, IDNs, and supported wildcards consistently. Reject invalid entries visibly.

### A16. A shortcut in an iframe also shows an incorrect parent-page message

Priority: P3. Evidence: released extension. Task: T16h.

`src/entrypoints/content.ts:99-103` uses `document.hasFocus()` to decide which frame handles the shortcut. The parent document also reports focus when a child frame has it.

Reproduction: focus the cross-origin editor iframe and send the same `open-popup` message used by the shortcut. The child opens its rewrite popup. The parent simultaneously displays `Click into a text field first.`

Fix: route the command to the focused editor frame, or suppress the parent response when focus belongs to a descendant frame. Verify one popup and no false toast for nested frames.

### A17. The privacy policy describes retention and keys inaccurately

Priority: P2. Evidence: source and policy comparison. Task: T17a.

`PRIVACY.md:22-23` says an answer is kept only while the rewrite popup is open. Idle slots in `src/content/idle.ts` retain original text, results, and `lastFull` outside the popup. This is memory retention, not evidence of LocalPolish saving drafts to disk.

`PRIVACY.md:64-65` says keys are never sent anywhere, but API adapters intentionally send the chosen key to the provider for authentication. The earlier API description is more accurate. General claims that every CLI has all tools off also need the documented Grok search exception kept beside them.

Fix: describe extension disk storage, temporary in-page memory, and CLI-managed history separately. Say that keys go only to their configured authentication endpoint. Review iframe and spellcheck claims after their fixes.

### A18. The full options page is missing the idle setting

Priority: P3. Evidence: released options page and source. Task: T17b.

The README says the full options page has the same settings as the toolbar popup. `src/options/App.tsx:30-37` renders no idle toggle, and `DefaultsSection` contains only default mode.

Reproduction: open the released `options.html`. There is no Fix while I type control. The toolbar popup has it.

Fix: add the setting to the full options page and share the existing setting behavior. A user must be able to turn automatic sending off from either settings page.

### A19. The editor test fixture pulls in a vulnerable dependency

Priority: P2. Evidence: npm dependency and advisory scans. Task: T17c.

`draft-js@0.11.7` pulls in `immutable@3.7.6`. `npm audit` reports two high-severity package entries: Immutable and its dependent Draft.js. These are development dependencies used by the editor fixture, not two vulnerable packages shipped in the release zip. The production-only audit is clean.

The advisories cover [prototype pollution](https://github.com/immutable-js/immutable-js/security/advisories/GHSA-wf6x-7x77-mvgw), [hash-collision denial of service](https://github.com/immutable-js/immutable-js/security/advisories/GHSA-xvcm-6775-5m9r), and [List overflow](https://github.com/immutable-js/immutable-js/security/advisories/GHSA-v56q-mh7h-f735).

Fix: verify a compatible patched Immutable 3.x override against the Draft.js fixtures, or isolate and replace the fixture dependency if needed. Recheck the current advisory ranges when implementing. Do not accept npm's suggested major Draft.js downgrade without checking behavior.

### A20. CI does not test the supported bridge operating systems

Priority: P2. Evidence: workflow and test conditions. Task: T17d.

`.github/workflows/test.yml:13-22` runs only Ubuntu and Node 24. `bridge/install.test.mjs:25` and `:119` restrict installer groups to macOS and Windows respectively. Neither group runs in that CI job. The package also promises Node 22 or newer, which the workflow does not exercise.

Fix: add targeted macOS and Windows bridge jobs and a Node 22 compatibility job. Keep the Linux browser suite. Add a real Windows tree-cleanup test instead of treating the skipped POSIX test as Windows coverage.

The audit did not run a fresh Windows browser or real CLI check. Earlier manual Brave results remain useful historical evidence, not a new validation.

### A21. Main has no enforced checks before changes land

Priority: P2. Evidence: authenticated GitHub reads. Task: T17e.

The main branch protection endpoint returned `Branch not protected`. Both branch rules and repository rulesets returned empty lists. CI runs on `push` only.

The current release checks are green. The gap is that a future failing change can still land on main before those checks finish. `RELEASING.md` states that main stays green, but repository settings do not enforce it.

Fix: add pull-request checks and a main ruleset requiring the existing gate. Confirm the intended direct-push policy before applying remote settings. Keep this as a planned administrative action. The audit changed no GitHub settings.

### A22. Release instructions miss rebase and describe bridge updates incorrectly

Priority: P3. Evidence: release guide and installer source. Task: T17f.

`RELEASING.md:67-71` pushes without the required `git pull --rebase` step. It also tags before any rebase, so a later rebase could leave the tag on the wrong commit.

Lines 87-89 say bridge changes reach users only after both pulling and reinstalling. The generated wrapper points directly at the clone's `bridge/host.mjs` in `bridge/install.mjs:48-65`. Pulling changes that code for the next bridge process even without reinstalling. Wrapper or registration changes still need installation.

Fix: update the release sequence to rebase before tagging and pushing, stop on conflicts, and recheck the commit being released. Explain live-checkout bridge updates accurately. Keep merged-branch cleanup and the protected branch exclusions in the procedure.

## Optimizations worth measuring

### O01. Reduce bridge checks when opening settings

`src/popup/useBridge.ts` checks on every toolbar popup mount, including API-only configurations. `bridge/host.mjs:67-73` starts up to three version commands sequentially. Each has a five-second timeout, while `pingBridge()` times out after ten seconds.

Check lazily for CLI providers or when the bridge card is requested. Run independent version probes in parallel under one deadline. A short cache with an explicit Check again action is enough. Measure popup startup and process counts before and after. There is no reason to keep a permanent bridge process without stronger evidence.

### O02. Reduce idle-marker polling and bound background work

`src/content/idle.ts:314-319` starts a 250-millisecond loop while marks exist. The loop reads editor text and layout repeatedly. Marks and caches can remain in long-lived tabs. Separate tabs can also each start a CLI process.

First measure work with one large editor, several marked fields, and background tabs. Pause work when disabled or hidden, prefer relevant resize and input events, and retain a fallback only where sites need it. Set a small per-provider concurrency limit if measurements show overlapping work is a problem. Never truncate a draft silently.

The released extension also leaves an adopted idle request running after its popup closes. That was observed, but retaining a background idle result may be intentional. Decide whether Close only hides it or an explicit Stop action cancels it. Do not call this a confirmed bug without settling that behavior.

### O03. Reuse the diff and warnings for a finished answer

`src/content/ui/Popup.tsx` computes `wordDiff()` when it renders a final answer. `popupNotes()` scans protected tokens again on state changes such as Copy. The diff already has a 200-millisecond timeout and a safe fallback.

Measure large drafts, then cache calculations by input and final answer if they repeat enough to matter. Preserve the timeout and fallback. The release is small, so a framework rewrite or bundle split is not justified by the current size.

## Test and documentation follow-up

Keep the existing behavior tests. Most mocks are at useful boundaries: Chrome APIs, HTTP, and CLI processes. The main weakness is missing scenarios, not a need to replace the suite.

Add regressions with each fix for frame identity, live setting changes, inherited spellcheck, late selection changes, line-break edits, concurrent settings writes, rejected storage saves, malformed settings, filtered streams, literal tags, and complete emoji sequences. Use real Chromium for DOM and frame behavior. Use real harmless processes for process-tree tests.

`src/core/prompts.test.ts` also pins particular instruction wording. Keep structural prompt tests, and put quality checks in a small fixed corpus. `bench/inputs.mjs` covers Fix only. Add Rephrase, Shorter, literal code, URLs with punctuation, emojis, and text that looks like instructions. Do not replace deterministic tests with paid model calls in ordinary CI.

Benchmark documents mix historical results with current decisions. Mark old defaults and obsolete bridge behavior as superseded. Link the current prompt and result set clearly. Do not rerun paid benchmarks as part of this audit.

## Limits and release checks still needed

- No fresh manual Gmail, X, LinkedIn, or GitHub checks were run against signed-in accounts.
- Real Claude, Codex, Grok, Anthropic, and remote OpenAI-compatible rewrites were not called. Version and flag compatibility still need live smoke checks with fixed sample text.
- Windows setup, registry behavior, browser behavior, and process-tree cleanup were not executed here.
- Screen-reader behavior, a full keyboard audit, and visual checks at browser zoom remain manual release work. One existing Home screenshot was inspected. Automated browser tests are not a complete accessibility audit.
- No malicious webpage was shown to read extension keys or execute arbitrary bridge commands. A06 and A08 have the specific setup conditions stated above.
- No production dependency advisory was reported. That does not prove the extension has no security defects.
- The credential check covered selected patterns in tracked files. It was not a full secret scan or a scan of Git history.

The next-release plan includes those checks. Nothing in this audit changes the version, publishes a release, changes remote settings, or starts implementation.
