## Work

1. Add `src/core/chatHistory.ts`. Use `chrome.storage.local` under a separate `chat-history` key. Export types and functions for saving, listing, opening, deleting one, deleting all, and pruning. Follow the storage adapter style in `src/core/settings.ts` and the existing settings lock. Use `navigator.locks` when available, with a module promise queue fallback, so updates from panel and background cannot overwrite each other. Serialize all operations that may write, including deletion and pruning. Do not silently ignore storage failures.
2. A saved chat has an id, title, createdAt, updatedAt, an optional attachment `{text,title,url}`, and a `turns` array of `{role:'user'|'assistant',content:string}`. Reuse `ChatTurn` and `ChatAttachment` from `src/core/prompts.ts`. Store plain data, never HTML. Let `saveChat` accept `{id?,title,turns,attachment?}` and return the saved record. Assign new ids with `crypto.randomUUID()` and timestamps with `Date.now()`. For updates, preserve the creation time. If an explicit id no longer exists, throw a clear error instead of resurrecting a deleted chat. Keep model/provider choices out of history for now; the existing chat settings own them.
3. Keep the 50 most recently updated chats. Expire a chat at 30 days since `updatedAt`, with `updatedAt <= now - 30 days` expired. Prune on every save and on browser startup. Listing and opening should also exclude expired records. Sort most recent first, with an id tie-breaker for equal timestamps. Delete-all clears only this key and never settings or usage.
4. Cap each serialized record at 128 KiB in UTF-8, including attachment, title, timestamps, id and turns. Fifty chats then use at most about 6.25 MiB plus array framing, leaving space for settings and usage. Reject a save that exceeds this cap with a clear error. Do not truncate a selection or answer silently. This is a history cap separate from the 256 KiB input and 1 MiB output limits. The future panel must show a save error without losing the answer. Note this decision in the plan.
5. Validate records read from storage: require a nonempty string id, string title, finite nonnegative timestamps with createdAt <= updatedAt, a turn array with only user or assistant string contents, and an optional attachment with exactly the three string fields. Drop malformed and oversized records and unknown fields. Deduplicate ids by keeping the newest valid record. Return fresh plain objects so callers cannot mutate storage or another read through aliases. The typed save input is trusted application input; do not add redundant schema checks for fields its type already guarantees. Validate its id existence and byte cap as described above.
6. Register `chrome.runtime.onStartup` pruning in `src/entrypoints/background.ts`, beside the existing onInstalled listener. Add the API to its local ExtensionChrome interface. Catch startup storage failures and log one short warning with the error, since no UI caller is awaiting that work. Keep current onInstalled setup behavior. In `src/background/entrypoint.test.ts`, extend `startBackground` with a real memory-backed storage get/set/remove stub and the startup event listener, and invoke that listener to prove expired history is removed and existing settings are untouched. Do not mock the history module under test.
