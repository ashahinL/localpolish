## Entry points

1. Add a content-script sparkle for selected page text. Reuse `FloatingButton`, `focusCaret`, `placeButton`, `guarded`, and the shared shadow root from `src/content/button.ts`, `caret.ts`, `position.ts`, and `ui/root.ts`. Give it its own layer, so it never replaces the existing Fix button. Show only for two or more whitespace-separated words outside editable fields. Check both ends of the selection and exclude input, textarea, contenteditable, and the extension's own UI. Hide on collapsed selection, scroll, resize, disabled setting, and blocked sites. Preserve the selection on mousedown. The existing root drops untrusted clicks; keep that protection. Send text, title and actual frame URL only after a trusted click. No AI request is made until the panel user asks.
2. Add a `selectionChat` boolean setting, default true, with checked reads and `pageSettings` propagation. Include it in content's strict settings validation and refresh the new sparkle when it changes. Add a simple checkbox in `DefaultsSection` in `src/options/sections.tsx`, using current styles: "Show chat button on selected page text". Its help says it applies outside text fields. Turning it off affects only the automatic selection sparkle. Menu, shortcut and toolbar remain available on blocked sites and when the setting is off.
3. Add the selection context menu "Ask LocalPolish about this" with `contextMenus` permission. Register it on install/update without duplicate ids. Its handler gets text from `info.selectionText` and the selection's frame/page URL and tab title. Open the panel immediately inside the user gesture handler before any await. Store a fresh attachment pending entry afterward. Errors must be handled, not left as rejected promises.
4. Add the `open-chat` command with Alt+Shift+L, including the mac binding. Keep the existing Polish command unchanged. The handler opens the panel immediately with the supplied tab/window id, then obtains selected text from the content script. If there is no selection, open a plain chat. Restricted pages without content scripts must still open a plain chat.
5. Add a compact "Open chat" button to the toolbar popup Home tab, using existing styles. It starts a plain chat with no attachment. Fetch the active tab/window identifiers before the click, so the click handler can call `sidePanel.open` directly with no preceding await. Write the pending entry through a worker message and close the popup only after the open call and pending write finish. Disable the button until its target is ready and show a clear error if it fails. This is a small control addition, not a popup redesign.

## Selection, windows and safety

T23a proved direct page-click runtime messages, the native context menu, real shortcut, and popup can open the panel. Call `sidePanel.open` before any await that can consume the gesture. Avoid opening an options or panel HTML tab as a fallback. If page-click opening rejects for a browser's gesture rule, show "Press the chat shortcut to open the chat" through `showToast`.

Selection reads for a shortcut must keep the correct frame even when opening the panel moves focus. The content script may cache its current selection locally on selectionchange. Report only a focused-frame hint to the worker on trusted focus/selection interactions; do not send the selection text before an explicit entry-point action. The worker can keep the latest frame id per tab in session storage so a restarted worker can recover it. Resolve the frame hint and read the cached selection after starting the panel open call. Clean up hints when tabs close. This also prepares the frame ownership needed by T23f. The top frame is a fallback if the hint is missing or the frame is gone. An empty/inaccessible selection means a plain chat. Do not add broad scripting or webNavigation permissions.

Pending attachments must belong to the opening browser window. The current `src/chat/pending.ts` uses one global `chat-pending` key and App keeps its tabId. Change to a key scoped by window id, such as `chat-pending:<windowId>`, and have the panel's watcher determine its own window before reading or following that key. Preserve its cold-start and newer-event-before-old-read protection. Do not let an entry point in another browser window reset this panel's conversation. Keep the payload `{sequence: string, tabId: number, attachment?: {text,title,url}}`; fresh sequences come from UUIDs. Toolbar writes an absent attachment even if text remains selected. Add a clear path for T23f to retrieve the associated tab/frame ids without reading DOM data attributes as application state.

Validate runtime messages and sender identity at the boundary. Page-originated opening and frame hints require a content-script sender with a tab id; popup plain-chat requests require this extension's own popup URL. Use the sender's tab/frame/URL rather than trusting page-supplied ids or URL claims. Keep the no-AI-until-asked rule. The automatic sparkle obeys the existing frame/ancestor blocklist policy. Explicit entry points remain usable when blocked. Session storage must remain restricted to trusted extension contexts.

Keep event logic in small dedicated content/background modules rather than growing the main entry points further. Reuse the current storage and runtime patterns. The existing `commands.onCommand` callback interface may need its optional tab argument. Required APIs can be added to the local Chrome interfaces and their test fakes. Do not weaken the existing sender checks on chat streaming ports.
